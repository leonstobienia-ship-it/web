# V2.5A - Consumo readonly na interface

Data: 2026-06-05

Branch: `dev/v2.3-sharepoint-integracao`

Commit base: `2250e21 docs: registrar validacao manual readonly v2.4f no tenant`

## Objetivo

Consumir gradualmente dados reais readonly do SharePoint na interface SPFx, sem redesenhar o fluxo homologado, sem escrita e sem alterar `src/prototype/app.js`.

Codex nao conectou ao SharePoint, nao publicou pacote, nao instalou app, nao alterou listas, permissoes ou dados e nao iniciou Power Automate.

## Estado anterior

A V2.4F validou manualmente no tenant que:

- `ENAC Usuarios Perfis` retorna GET/fetch 200;
- `ENAC Alcadas` retorna GET/fetch 200;
- a webpart renderiza em pagina restrita;
- nao houve evidencia de `POST`, `MERGE`, `PATCH` ou `DELETE`.

Antes da V2.5A, os dados readonly ja eram carregados em estado interno, mas a interface ainda usava predominantemente mocks/fallback.

## Areas ajustadas

### Dashboard

Os cards prioritarios passam a usar `requisicoesResumo` do SharePoint quando `origemDadosEfetiva = "sharepoint"`:

- `Solicitacoes ativas`;
- `Aguardando cotacao`;
- `Aguardando aprovacao`.

Se o carregamento readonly falhar, os cards continuam usando `solicitacoes` locais.

### Administracao - Usuarios

A tela existente `adminUsuarios` passa a renderizar `ENAC Usuarios Perfis` em modo readonly quando os dados SharePoint estiverem carregados.

Campos exibidos:

- Nome;
- Usuario interno;
- Perfil;
- Cargo/funcao;
- Status ativo/inativo.

E-mails reais nao sao exibidos por padrao nesta tela.

### Administracao - Alcadas

A tela existente `adminAlcadas` passa a renderizar `ENAC Alcadas` em modo readonly quando os dados SharePoint estiverem carregados.

Campos exibidos:

- Regra interna;
- Processo;
- Tipo de solicitacao;
- Faixa de valor em Real brasileiro;
- Aprovador principal;
- Status ativa/inativa.

Nao ha criar, editar ou excluir.

### Administracao - Historico

A tela existente `adminHistorico` tenta usar `ENAC Historico Configuracoes` por leitura readonly. Se a lista nao retornar dados ou falhar, permanece em fallback local.

## Diagnostico e fallback

A V2.5A preserva:

- `origemDadosEfetiva`;
- `erroReadonly`;
- diagnostico em console debug;
- fallback local.

O console debug registra:

- fonte usada nos cards;
- contagem de usuarios/perfis;
- contagem de alcadas;
- contagem de requisicoes resumo;
- contagem de historico carregado;
- fallback quando houver erro.

Nao ha exposicao deliberada de e-mails reais no console.

## Escrita bloqueada

A V2.5A nao adiciona escrita:

- sem `spHttpClient.post`;
- sem `POST`;
- sem `MERGE`;
- sem `PATCH`;
- sem `DELETE`;
- sem PnP write;
- sem chamada a `persistirSnapshotAprovacaoCompra()`;
- sem criacao ou vinculo de snapshot;
- sem preenchimento de `SnapshotAprovacaoCompra`.

## Areas ainda em fallback/mock

Permanecem locais nesta rodada:

- formulario de nova solicitacao;
- fluxo de cotacao;
- aprovacoes operacionais;
- pedido de compra;
- financeiro;
- liberacao bancaria;
- historico operacional da solicitacao;
- criacao/snapshot de processo.

Essas areas nao foram migradas para evitar ampliar escopo visual ou introduzir escrita.

## Riscos

- Os nomes/status vindos do SharePoint podem variar; os cards usam normalizacao simples para `Aguardando cotacao` e `Aguardando aprovacao`.
- Historico administrativo real pode estar vazio; nesse caso a tela usa fallback local.
- Validacao real depende de substituicao manual do pacote no App Catalog por Leon.

## Criterios de sucesso

- Build SPFx local passa.
- Pacote SHIP e gerado localmente.
- Dashboard mostra contadores reais quando SharePoint readonly estiver disponivel.
- Admin usuarios e alcadas exibem dados reais readonly ou fallback seguro.
- Network nao mostra escrita da webpart.
- Visual basico homologado permanece preservado.
