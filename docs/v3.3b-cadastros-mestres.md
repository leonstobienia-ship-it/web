# V3.3B - Cadastros Mestres Operacionais

## Objetivo

Transformar os cadastros mestres principais do ERP ENAC em operacao real local, usando backend Node.js/TypeScript, PostgreSQL local e frontend React/Vite.

Esta etapa continua restrita a desenvolvimento local. Nao ha escrita real no SharePoint, alteracao de permissoes Entra, automacoes, banco de producao ou `DELETE` fisico.

## Escopo entregue

- CRUD local de clientes.
- CRUD local de fornecedores.
- CRUD local de centros de custo.
- CRUD local de obras.
- Inativacao e reativacao logica por `status`.
- Erros JSON padronizados.
- Queries parametrizadas via `pg`.
- Validacao backend de campos obrigatorios, UUID, status, tipo de pessoa, UF, datas e numeros.
- CORS local para frontend Vite.
- Frontend operacional em `web/src/features/cadastros`.
- Servico de API em `web/src/services/erpApi.ts`.
- Migration incremental `database/migrations/002_cadastros_mestres.sql`.

## Migration

A migration `002_cadastros_mestres.sql` adiciona campos necessarios para a operacao dos cadastros:

- `clientes`: `tipo_pessoa`, `endereco`.
- `fornecedores`: `tipo_pessoa`, `categoria`, `endereco`.
- `centros_custo`: `tipo`, `observacoes`.
- `obras`: `cidade`, `uf`, `responsavel`, `valor_previsto`, `observacoes`.

Tambem adiciona checks para status/tipo e indices por `company_id, status`.

O runner `server/src/db/migrate.ts` agora executa todas as migrations `*.sql` versionadas em ordem e registra cada uma em `schema_migrations`.

## Frontend

A area `Cadastros` foi adicionada ao portal Vite preservando a navegacao V3.1. Ela permite:

- listar registros;
- criar registros;
- editar registros;
- inativar registros;
- reativar registros inativos;
- visualizar mensagens de erro;
- visualizar carregamento e estado vazio.

A configuracao local esperada e:

```text
VITE_ENAC_ERP_API_BASE_URL=http://127.0.0.1:3333
```

## Regras de seguranca da etapa

- Escrita limitada ao PostgreSQL local `enac_erp_dev`.
- API bloqueia `DATABASE_URL` fora de `localhost`, `127.0.0.1` ou `::1`.
- Nenhum endpoint `DELETE` foi criado.
- Inativacao usa `status = 'inativo'`.
- Reativacao usa `status = 'ativo'`.
- `.env` permanece local e ignorado.
- SharePoint, Entra e automacoes permanecem fora do escopo.

## Testes funcionais locais

Todos os registros criados na validacao devem conter o marcador:

```text
DEV_LOCAL_V3_3B
```

Roteiro minimo:

1. Rodar migrations.
2. Subir backend local.
3. Criar cliente com marcador `DEV_LOCAL_V3_3B`.
4. Editar o cliente.
5. Inativar o cliente.
6. Reativar o cliente.
7. Criar fornecedor com marcador `DEV_LOCAL_V3_3B`.
8. Criar centro de custo com marcador `DEV_LOCAL_V3_3B`.
9. Criar obra vinculada ao cliente e centro de custo com marcador `DEV_LOCAL_V3_3B`.
10. Confirmar os registros nas listas.

## Validacao local concluida

Validacao executada em ambiente local com PostgreSQL Docker `enac-erp-postgres-dev` healthy:

- `docker compose ps` confirmou container local ativo.
- `npm run migrate` aplicou `002_cadastros_mestres`.
- `npm run build` no backend passou.
- `npm run web:build` passou.
- `npx tsc -p web/tsconfig.json --noEmit` passou.
- `npx tsc -p tsconfig.json --noEmit` passou.
- `GET /health` retornou `200 OK`.
- `GET /health/db` retornou `database.connected = true` e `database.name = enac_erp_dev`.
- `GET /clientes`, `/fornecedores`, `/obras` e `/centros-custo` retornaram dados locais.
- Cliente `DEV_LOCAL_V3_3B` foi criado, editado, inativado e reativado.
- Fornecedor, centro de custo e obra `DEV_LOCAL_V3_3B` foram criados.
- A obra foi vinculada ao cliente e ao centro de custo criados na rodada.

Observacao: a primeira tentativa de migration falhou por divergencia entre `.env` local e credenciais do container ja existente. A validacao foi repetida com variaveis de ambiente transitorias lidas do container local, sem alterar `.env`.
